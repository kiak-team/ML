# 데이터 설명

교수님이 제공한 pkl 파일 3개를 정리한 문서다. 아래 수치는 모두 `code/check_data.py`와 `code/explore.py`로 원본에서 직접 계산한 값이며, 로그는 `logs/`에 있다.

## 1. 파일 구성

| 파일 | 크기 | 형태 | 내용 |
|---|---|---|---|
| `mon_standard.pkl` | 717MB | `dict` {URL 번호 0~949: 기록 20개 리스트} | **감시 대상(monitored)** 사이트 방문 기록 19,000개 |
| `unmon_standard10.pkl` | 428MB | `list` (기록 10,000개) | **감시 대상이 아닌(unmonitored)** 사이트 방문 기록. 라벨 없음 |
| `unmon_standard10_3000.pkl` | 130MB | `list` (기록 3,000개) | `unmon_standard10.pkl`의 **앞 3,000개와 완전히 같음** (확인 완료). 빠른 실험용 축소판 |

pkl 파일은 용량 제한 때문에 GitHub에 올리지 않는다. 각자 내려받아 임의의 폴더에 두고 경로만 넘기면 된다.

### mon 구조: 사이트 95개 × URL 10개 × 방문 20회

```
URL 번호 i (0~949)
 ├─ 사이트 번호 = i // 10  (0~94)   ← 예측할 라벨
 └─ 방문 기록 20개 (inst 0~19)
```

- 사이트 하나에 URL 10개(같은 사이트의 서로 다른 페이지)가 있고, URL마다 20번 방문했다.
- 따라서 사이트마다 정확히 **200개**이며 클래스 불균형이 없다.
- `USE_SUBLABEL=True`로 두면 URL 번호 자체(950개 클래스)를 라벨로 쓸 수 있다. 기본값은 사이트 95개다.

## 2. 기록 하나의 형태

기록 하나는 숫자 리스트이고, 숫자 하나가 Tor 셀(512바이트) 하나다.

```
[0.0, -0.14, 0.14, -0.31, 0.31, -0.51, 0.51, 0.51, -0.75, ...]
```

- **절댓값** = 첫 셀 기준 상대 시각(초)
- **부호** = 방향. `+`는 송신(클라이언트 → 서버), `-`는 수신(서버 → 클라이언트)
- 셀 크기 정보는 없다. Tor 셀은 크기가 고정이므로 512로 둔다.

### 팀 공통 규칙 (교수님 `load_pickle_code.ipynb`와 동일)

| 항목 | 규칙 | 코드 |
|---|---|---|
| 라벨 | `i // 10` (사이트 95개) | `load_data.site_label()` |
| 방향 | `c > 0`이면 +1(송신), 아니면 -1(수신) | `load_data.direction()` |
| 시간 | `abs(c)` | `load_data.convert()` |
| 크기 | 방향 × 512 | `load_data.convert()` |

**첫 셀 주의**: 모든 기록의 첫 값이 `0.0`이다. 시각이 0이라 부호로 방향을 알 수 없으므로, 위 규칙에 따라 **수신(-1)** 으로 처리한다. 강의 슬라이드 13쪽 예시(`0.0  -512`)와도 일치한다.

`code/load_data.py`로 읽으면 노트북과 결과가 같다. 29,000개 기록 전부를 비교해 불일치가 0개임을 확인했다(`logs/check_data.log`).

## 3. 기본 통계

| 항목 | mon (19,000개) | unmon (10,000개) |
|---|---|---|
| 기록 길이 최소 | 50 | 51 |
| 기록 길이 25% | 1,530 | 1,459 |
| 기록 길이 중앙값 | 3,309 | 4,193 |
| 기록 길이 75% | 6,378 | 8,234 |
| 기록 길이 95% | 9,963 | 9,973 |
| 기록 길이 최대 | 9,993 | 9,992 |
| 지속 시간 중앙값 | 26.0초 | 18.9초 |
| 지속 시간 95% | 56.9초 | 52.2초 |
| 지속 시간 최대 | 86.0초 | 55.5초 |
| 기록별 송신 비율 중앙값 | 9.0% | 7.9% |
| 전체 셀 수 | 79,587,362 | 47,562,088 |

- 분위수는 정렬된 배열에서 `int(p × 개수)`번째 값을 그대로 고른 값이다(보간 없음).
- 지속 시간 = 마지막 셀의 시각.
- 송신 비율은 기록별로 계산한 뒤 그 중앙값을 낸 것이다. 웹페이지를 내려받는 과정이므로 대부분 수신이다.

## 4. 품질 점검 결과

| 점검 | mon | unmon |
|---|---|---|
| 빈 기록 / 50셀 미만 | 0 / 0 | 0 / 0 |
| 10,000셀 이상 | 0 | 0 |
| 9,900~9,999셀 | 2,209 (11.6%) | 1,787 (17.9%) |
| 50~59셀 | 168 | 136 |
| NaN·무한대 | 0 | 0 |
| 시간이 역행하는 기록 | 0 | 0 |
| 0.01초 단위에서 벗어난 값 | 0 | 0 |
| 첫 값이 `0.0` | 19,000 (전부) | 10,000 (전부) |
| 두 번째 셀이 수신 | 19,000 (전부) | 10,000 (전부) |

해석:
- **길이가 약 10,000에서 잘린 것으로 보인다.** 10,000 이상은 없고 9,900대에 몰려 있다. 50 미만도 없어 짧은 기록은 걸러낸 것으로 보인다. 다만 수집 코드가 없어 확정할 수는 없다.
- **시간 해상도가 0.01초다.** 그래서 같은 시각에 찍힌 셀이 매우 많다. 직전 셀과 시각이 같은 비율은 mon 전체 93.33%(기록별 중앙값 92.30%), unmon 전체 94.28%다. 시간 피처의 유효성은 실험으로 확인해야 한다.
- mon과 unmon은 길이·지속 시간 분포가 다르다(unmon이 더 길고 더 빨리 끝난다). 수집 환경이 달랐을 수 있으므로 open-world 결과 해석 시 주의한다.

- **마지막 방문(inst 19)은 다른 방문보다 짧고 느리다.** 길이 중앙값은 2,340(다른 방문 약 3,400), 지속 시간 중앙값은 40.7초(약 25초)다. 이 때문에 현재 test 분할(inst 18~19)은 정확도가 낮게 나온다. 자세한 내용은 [PREPROCESSING.md](PREPROCESSING.md)의 "마지막 방문" 절에 있다.
