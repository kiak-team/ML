# 데이터 설명

교수님이 주신 pkl 파일 3개를 정리한 문서예요. 아래 수치는 모두 `code/check_data.py`와 `code/explore.py`로 원본을 직접 계산한 값이고, 로그는 `logs/`에 있어요.

## 1. 파일 구성

| 파일 | 크기 | 형태 | 내용 |
|---|---|---|---|
| `mon_standard.pkl` | 717MB | `dict` {URL 번호 0~949: 기록 20개 리스트} | **감시 대상(monitored)** 사이트 방문 기록 19,000개 |
| `unmon_standard10.pkl` | 428MB | `list` (기록 10,000개) | **감시 대상이 아닌(unmonitored)** 사이트 방문 기록. 라벨 없음 |
| `unmon_standard10_3000.pkl` | 130MB | `list` (기록 3,000개) | `unmon_standard10.pkl`의 **앞 3,000개와 완전히 같음** (확인함). 빠르게 실험할 때 쓰는 축소판 |

pkl 파일은 GitHub에 올리지 않아요(용량 제한). 각자 다운로드해서 아무 폴더에 두고 경로만 넘기면 돼요.

### mon 구조: 사이트 95개 × URL 10개 × 방문 20회

```
URL 번호 i (0~949)
 ├─ 사이트 번호 = i // 10  (0~94)   ← 우리가 맞혀야 할 라벨
 └─ 방문 기록 20개 (inst 0~19)
```

- 사이트 하나에 URL 10개(같은 사이트의 서로 다른 페이지), URL마다 20번 방문했어요.
- 그래서 사이트마다 정확히 **200개**씩이고, 클래스 불균형이 없어요.
- `USE_SUBLABEL=True`로 두면 URL 번호 자체(950개 클래스)를 라벨로 쓸 수도 있어요. 기본값은 사이트 95개예요.

## 2. 기록 하나는 어떻게 생겼나

기록 하나 = 숫자 리스트예요. 숫자 하나가 Tor 셀(512바이트) 하나예요.

```
[0.0, -0.14, 0.14, -0.31, 0.31, -0.51, 0.51, 0.51, -0.75, ...]
```

- **절댓값** = 첫 셀 기준 상대 시각(초)
- **부호** = 방향. `+`는 송신(내 컴퓨터 → 서버), `-`는 수신(서버 → 내 컴퓨터)
- 셀 크기 정보는 들어 있지 않아요. Tor 셀은 크기가 고정이라서 512로 놓아요.

### 팀 공통 규칙 (교수님 `load_pickle_code.ipynb`와 같음)

| 항목 | 규칙 | 코드 |
|---|---|---|
| 라벨 | `i // 10` (사이트 95개) | `load_data.site_label()` |
| 방향 | `c > 0`이면 +1(송신), 아니면 -1(수신) | `load_data.direction()` |
| 시간 | `abs(c)` | `load_data.convert()` |
| 크기 | 방향 × 512 | `load_data.convert()` |

**첫 셀 주의**: 모든 기록의 첫 값이 `0.0`이에요. 시각이 0이라서 부호로 방향을 알 수 없는데, 위 규칙에 따라 **수신(-1)** 으로 처리해요. 강의 슬라이드 13쪽 예시(`0.0  -512`)와도 같아요.

`code/load_data.py`로 읽으면 노트북과 결과가 같아요. 29,000개 기록 전부를 비교해서 다른 기록이 0개인 것을 확인했어요(`logs/check_data.log`).

## 3. 기본 통계

| 항목 | mon (19,000개) | unmon (10,000개) |
|---|---|---|
| 기록 길이 최소 | 50 | 51 |
| 기록 길이 25% | 1,530 | 1,459 |
| 기록 길이 중앙값 | 3,309 | 4,193 |
| 기록 길이 75% | 6,378 | 8,234 |
| 기록 길이 95% | 9,963 | 9,973 |
| 기록 길이 최대 | 9,993 | 9,992 |
| 지속 시간 중앙값 | 26.0초 | 18.9초 |
| 지속 시간 95% | 56.9초 | 52.2초 |
| 지속 시간 최대 | 86.0초 | 55.5초 |
| 기록별 송신 비율 중앙값 | 9.0% | 7.9% |
| 전체 셀 수 | 79,587,362 | 47,562,088 |

- 분위수는 정렬한 배열에서 `int(p × 개수)`번째 값을 그대로 고른 값이에요(보간 안 함).
- 지속 시간 = 마지막 셀의 시각.
- 송신 비율은 기록마다 따로 계산한 다음 그 중앙값을 낸 거예요. 대부분 수신이에요(웹페이지를 내려받으니까요).

## 4. 품질 점검 결과

| 점검 | mon | unmon |
|---|---|---|
| 빈 기록 / 50셀 미만 | 0 / 0 | 0 / 0 |
| 10,000셀 이상 | 0 | 0 |
| 9,900~9,999셀 | 2,209 (11.6%) | 1,787 (17.9%) |
| 50~59셀 | 168 | 136 |
| NaN·무한대 | 0 | 0 |
| 시간이 거꾸로 가는 기록 | 0 | 0 |
| 0.01초 단위에서 벗어난 값 | 0 | 0 |
| 첫 값이 `0.0` | 19,000 (전부) | 10,000 (전부) |
| 두 번째 셀이 수신 | 19,000 (전부) | 10,000 (전부) |

여기서 알 수 있는 것:
- **길이가 약 10,000에서 잘린 것으로 보여요.** 10,000 이상은 하나도 없고 9,900대에 몰려 있어요. 50 미만도 하나도 없어서, 너무 짧은 기록은 걸러낸 것 같아요. 둘 다 수집 코드가 없어서 확정할 수는 없어요.
- **시간 해상도가 0.01초예요.** 그래서 같은 시각에 찍힌 셀이 아주 많아요. 바로 앞 셀과 시각이 같은 비율이 mon 전체 93.33%(기록별 중앙값 92.30%), unmon 전체 94.28%예요. 시간 피처가 얼마나 쓸모 있을지는 실험해봐야 알아요.
- mon과 unmon은 길이와 지속 시간 분포가 서로 달라요(unmon이 더 길고 더 빨리 끝나요). 수집 환경이 달랐을 수 있으니, open-world 실험 결과를 해석할 때 주의해야 해요.

## 5. 아직 확인하지 않은 것

- 사이트별 길이 분포 그래프, mon/unmon 분포 비교 그래프
- 길이를 자르는 기준(예: 5,000)을 정했을 때 잘리는 기록 비율과 버려지는 셀 비율
- 중복 기록 여부
