# Extra credit: TrafficSliver 방어 깨기 — 데이터 전처리·피처 정리

2026-11-10 작성, 11/15 2단계 추가(5절). join 파일 규칙과 첫 결과는 [EXTRA_JOIN.md](EXTRA_JOIN.md)에 따로 정리했다.

## 요약

- 조교가 준 데이터는 BigEnough 데이터셋에 TrafficSliver BWR(경로 5개)을 적용한 것이다. 방문 1회가 split 파일 5개 + join 파일 1개다.
- 공격자는 입구 노드 하나만 본다고 가정하므로 **split 파일 하나가 instance 하나**다.
- 95-class closed-world, RF(200) 기준:

| 피처 | 정확도 |
|---|---|
| 방어 없음 (join→join, 기존 피처 375개) | 89.3% |
| 방어 있음 (split→split, 기존 피처 375개) | 7.5% |
| 방어 있음, `@timing` 18개만 | 10.4% |
| 방어 있음, `@timing` + 새 시간 피처 124개 (142개) | 15.5% |
| **방어 있음, 위에서 tnorm을 40등분 수신·송신으로 (202개, 11/15)** | **16.5%** (시드 1: 16.6%) |

  찍으면 1.05%다. 방어가 강하지만, 시간 피처로 처음 기준의 2배 넘게 올렸다.
- open-world(mon vs unmon)에서는 수집 환경 차이가 보이지 않는다. 피처 하나로 낸 AUC는 최대 0.555다.
  pkl 데이터처럼 앞 몇 셀을 잘라낼 필요가 없다.

## 1. 데이터

| | mon | unmon |
|---|---|---|
| 원본 zip | `mon.zip` (사이트 0–94 × 방문 0–199) | `unmon.zip` (0–18999) |
| 방문 수 | 19,000 | 19,000 |
| 파일 이름 | `{사이트}-{방문}_split_{0-4}.cell`, `_join.cell` | `{번호}_split_{k}.cell`, `_join.cell` |
| 빈 split (뺐다) | 7,962 (8.4%) | 9,953 (10.5%) |
| 쓰는 split | 87,038 | 85,047 |

- 한 줄은 `시간\t방향(±1)\t크기(±512)`이고, 크기는 항상 512다. 기존 pkl 규칙(방향 × 512)과 같다.
- split의 시간은 join의 시계를 그대로 가지고 있다. 파일마다 첫 셀이 0이 되도록 맞췄다.
- split 길이는 중앙값 mon 530셀 / unmon 612셀, 약 9초다(95%가 48초 이내). 빈 split을 뺀 뒤 50셀 미만은 mon 6.6% / unmon 7.3%다.
  (11/15 정정: 이전에는 "중앙값 약 400셀, 50셀 미만 약 16%"라고 적었다. `logs/sequences_sliver.log`로 다시 셌다.)
- 줄인 zip(`mon_25`, `unmon_5000` 등)은 쓸 필요가 없었다. 전체 데이터를 numpy로 바꾸면 RAM에 들어간다.

- mon과 unmon은 따로 실행한다. 둘을 한꺼번에 메모리에 올리면 약 1.7GB가 든다.

## 3. 분할 규칙 (누수 방지)

- 같은 방문의 split 5개와 join은 `group` 값이 같다. **train/test와 CV fold는 반드시 group 단위로 나눈다.**
  같은 방문의 조각이 양쪽에 들어가면 점수가 부풀려진다.
- 최종 test는 `ld.sliver_is_test(group)`, 방문의 10%다. 사이트마다 18–23개가 들어가고, 정수 해시라 언제 돌려도 같다. 튜닝 중에는 보지 않는다.
- 빠른 비교(`screen_sliver.py`)는 test를 뺀 방문 중 20%를 검증용으로 쓰는 holdout 1번이다.
  기존 피처 375개로 7.58%가 나와 5-fold 값(7.46%)과 맞는다.

## 4. 결과

### 4.1 기준선 (5-fold, 기존 피처 375개)

| | 정확도 |
|---|---|
| A join→join (방어 없음) | 89.3% ± 0.6 |
| B split→split (방어 있음) | 7.5% ± 0.1 |
| C join→split | 1.4% ± 0.1 |

C가 찍는 수준이다. 방어 전 데이터로 학습한 모델은 split에 통하지 않으므로 학습도 split으로 한다.

### 4.2 split에서 쓸모 있는 피처

- 그룹을 섞었을 때 정확도 하락은 `@timing` −5.0%p, `@cumul100` −2.6%p이고, 나머지 그룹은 0에 가깝다.
- 방어가 없을 때 핵심이던 방향·순서 피처(`@early`, `@bseq`, `@dir`)는 쓸모없다.
  BWR이 셀 묶음을 무작위 경로로 보내서, 한 경로 안의 셀 순서가 사이트와 무관해지기 때문으로 보인다.

### 4.3 새 시간 피처 (`features_time.py`, 124개)

| 그룹 | 개수 | 내용 |
|---|---|---|
| `tcum` | 38 | 고정 시각(0.25–60초)까지 받은/보낸 셀 수 |
| `tbin` | 40 | 처음 10초를 0.5초 칸으로 나눈 칸별 수신/송신 셀 수 |
| `tnorm` | 20 | 기록 길이를 20등분한 시각까지 받은 셀 비율 (시간 축 CUMUL). **11/15부터 40등분 수신·송신 80개**(5.1) |
| `gap` | 26 | 셀 사이 빈 시간: 임계값별 개수, 가장 긴 10개, 0.2초 넘는 빈 시간이 처음 10번 시작한 시각 |

### 4.4 피처 세트 비교 (holdout, RF 200, 95-class)

| 세트 | 개수 | 정확도 |
|---|---|---|
| 기존 전체 | 375 | 7.6% |
| `@timing` | 18 | 10.4% |
| `@timing @cumul100` | 118 | 7.9% |
| 새 시간 피처만 | 124 | 14.6% |
| **`@timing` + 새 시간** | **142** | **15.5%** |
| `@timing @cumul100` + 새 시간 | 242 | 14.3% |
| `@timing @cumul100 @count @burst` + 새 시간 | 257 | 14.6% |
| 전체 | 499 | 13.8% |
| `@timing` + `tcum` | 56 | 11.3% |
| `@timing` + `tbin` | 58 | 11.9% |
| `@timing` + `tnorm` | 38 | 14.0% |
| `@timing` + `gap` | 44 | 12.5% |

- **피처를 줄일수록 좋아진다.** 쓸모없는 피처가 많으면 RF가 분기마다 무작위로 고르는 후보에 좋은 피처가 덜 들어간다.
- `@cumul100`은 5-fold에서 그룹을 섞었을 때는 중요하게 나왔지만, 넣으면 오히려 떨어진다. 피처 100개가 시간 피처를 묻어 버리는 것으로 보인다.
- 새 시간 피처 중 `tnorm`이 피처 20개로 +3.6%p를 올려 효과가 가장 크다. 기록 길이와 무관한 "로딩 곡선 모양"에 정보가 남아 있다.
- 피처 500개 전체 기준 중요도 상위: `iat_max`, `gap_top_01~10`, `iat_zero_frac`, `duration`.

### 4.5 open-world 수집 환경 차이 확인 (split만, mon vs unmon 이진)

| 세트 | AUC |
|---|---|
| 전체 (499) | 0.805 |
| `@timing` + 새 시간 (142) | 0.816 |

- 피처 하나로 낸 AUC는 최대 0.555(`tnorm_in_*`)다. 한두 피처로 mon/unmon이 갈리는 수집 차이 신호가 없다.
  pkl 데이터에서는 앞 14셀만으로 AUC 1.0이 나왔다.
- 이진 분류에 쓰인 상위 피처는 `tcum_in_1.5~3`(처음 1.5–3초에 받은 셀 수)과 `gap_at_02~04`다.

## 5. 2단계 (11/15): 시간 피처 추가, 짧은 split, 시퀀스

`python -I -W ignore -X utf8 code/sliver_stage2.py <Downloads>/sliver_mon.npz > logs/sliver_stage2.log` (약 24분)
screen_sliver.py와 같은 holdout(최종 test 제외, 나머지 방문의 20%를 검증)과 RF(200)를 썼다. 기준은 `@timing` + 새 시간 142개(15.5%)다.
검증 15,771행에서 정확도 15%의 표준오차는 약 0.3%p다. 그래서 **+0.5%p 이상이고 시드 2개에서 같은 방향이면 채택**하기로 실험 전에 정했다.

### 5.1 시간 피처 후보 → 40등분 수신·송신 채택

| 세트 | 개수 | 시드 0 | 차이 | 시드 1 |
|---|---|---|---|---|
| S0 기준 (`@timing` + 새 시간) | 142 | 15.48% | | 14.99% |
| S1 + `tnorm_out` (송신 쪽 20등분) | 162 | 15.79% | +0.32 | |
| S2 `tnorm_in`을 40등분으로 | 162 | 15.53% | +0.06 | |
| **S3 40등분 수신 + 송신 (`tnorm_in` 20등분 대신)** | **202** | **16.46%** | **+0.98** | **16.57% (+1.58)** |

- 송신 쪽만 더하거나(S1), 수신만 촘촘하게 하면(S2) 차이가 표준오차 수준이다. **둘을 함께 하면(S3) 시드 2개 모두 +1%p 이상**이라 채택했다.
  수신과 송신의 로딩 곡선을 함께 촘촘하게 볼 때 정보가 생긴다.
- `features_time.py`의 `tnorm`을 40등분 수신·송신(80개, 이름 `tnorm_in_0025`~`tnorm_in_1000`, 끝 4자리 = 천분율)으로 바꾸고,
  `features/sliver_mon.csv`, `sliver_unmon.csv`를 다시 만들었다. **새 후보 = `@timing` + 새 시간 184개 = 202개.**
- 이전 로그(`screen_sliver.log`)의 `tnorm_in_005`~`tnorm_in_100`(20등분) 이름은 더 이상 CSV에 없다.
  `sliver_stage2.py`는 옛 CSV를 전제로 한 기록용이다. 다시 돌리려면 `features_time.py`를 e3c098e 버전으로 되돌려 CSV를 만든다.

### 5.2 짧은 split → 그대로 둔다

S0, 시드 0. 길이 구간별 검증 정확도다. "50셀 이상만 학습"은 50셀 미만 split을 학습에서만 뺀 것이다(검증은 같다).

| 길이(셀) | 검증 비율 | 전체로 학습 | 50셀 이상만 학습 |
|---|---|---|---|
| 0~9 | 1.2% | 5.2% | 1.6% |
| 10~19 | 1.3% | 14.9% | 1.4% |
| 20~49 | 4.2% | 19.0% | 10.2% |
| 50~99 | 7.4% | 11.8% | 12.2% |
| 100~199 | 11.0% | 13.2% | 13.2% |
| 200~499 | 22.5% | 14.6% | 14.4% |
| 500~999 | 21.0% | 14.0% | 14.0% |
| 1000~1999 | 18.3% | 17.6% | 18.4% |
| 2000~ | 13.0% | 20.4% | 20.6% |
| **50 미만** | 6.7% | **15.7%** | 6.9% |
| **50 이상** | 93.3% | 15.5% | 15.7% (+0.2) |
| 전체 | 100% | **15.5%** | 15.1% |

- **50셀 미만 split도 평균만큼 맞힌다**(15.7%, 찍기 1.05%). 10셀 미만만 거의 못 맞힌다(5.2%, 1.2%).
- 학습에서 빼면 짧은 split 정확도가 15.7% → 6.9%로 떨어진다. 긴 split은 +0.2%p로 표준오차 안이라 얻는 것이 없다.
- 그래서 **학습·평가 모두 그대로 둔다.** 공격자는 입구 노드에서 본 조각을 길이와 상관없이 분류해야 하므로, 평가에서 빼는 것도 맞지 않다.

### 5.3 split 시퀀스 (NN용) → L = 3,000, 방향 + 시각

`python -I -X utf8 code/sequences_sliver.py <Downloads>/sliver_mon.npz <Downloads>/sliver_seq_mon_L3000.npz` (unmon도, 각 1~2분, `logs/sequences_sliver.log`)

| L | 잘리는 split (mon / unmon) | 남는 셀 (mon / unmon) |
|---|---|---|
| 1,000 | 30.7% / 36.0% | 61.2% / 56.1% |
| 2,000 | 12.7% / 16.7% | 83.3% / 79.9% |
| **3,000** | **5.6% / 8.0%** | **92.8% / 91.1%** |
| 5,000 | 1.1% / 1.5% | 98.9% / 98.8% |

- 중앙값(530셀) 근처로 L을 잡으면 split의 절반이 잘린다. 그래서 **95% 가까이 잘리지 않는 3,000**으로 정했다. 압축 저장으로 파일은 각 약 80MB다.
- 내용: `dir` (n, 3000) int8 (+1 송신, −1 수신, 0 채움), `t_ms` (n, 3000) uint16 (첫 셀 기준 밀리초, 65,535 = 65.5초 상한, 이에 걸리는 split은 mon 0.23%), `label`, `group`, `part`, `length`, `is_test`.
- split에서는 방향 순서보다 시간에 정보가 남으므로(4.2) 시각을 함께 넣었다. 쓸 때는 `t_ms / 1000`(초)이다. 원본과 대조해 방향은 일치, 시각 오차는 0.5ms 이하임을 확인했다.
- NN을 쓸지, 어떤 구조로 쓸지는 모델 담당이 정한다. L은 `--length`로 바꿀 수 있다.
