# Extra credit: TrafficSliver 방어 깨기 — 데이터 전처리·피처 정리

2026-11-10 작성, 11/15 2단계 추가(5절), 11/19 3단계 추가(4.6–4.12). join 파일 규칙과 첫 결과는 [EXTRA_JOIN.md](EXTRA_JOIN.md)에 따로 정리했다.

## 요약

- 조교가 준 데이터는 BigEnough 데이터셋에 TrafficSliver BWR(경로 5개)을 적용한 것이다. 방문 1회가 split 파일 5개 + join 파일 1개다.
- 공격자는 입구 노드 하나만 본다고 가정하므로 **split 파일 하나가 instance 하나**다.
- 95-class closed-world, RF(200) 기준:

| 피처 | 정확도 |
|---|---|
| 방어 없음 (join→join, 기존 피처 375개) | 89.3% |
| 방어 있음 (split→split, 기존 피처 375개) | 7.5% |
| 방어 있음, `@timing` 18개만 | 10.4% |
| 방어 있음, `@timing` + 새 시간 피처 124개 (142개) | 15.4% |
| **방어 있음, tnorm을 40등분 수신·송신으로 (202개, 최종)** | **16.1%** (5-fold) / **17.0%** (test) |
| 방어 있음, 142개 + 송신 쪽 시간 피처 60개 (202개, 11/19) | 16.0% (5-fold) / 16.5% (test) |

  찍으면 1.05%다. 방어가 강하지만, 시간 피처로 처음 기준의 2배를 넘겼다.
  202개짜리 세트가 두 개였는데(11/15의 5.1, 11/19의 4.7) 같은 fold에서 맞대결한 결과
  **무승부라서 구현이 단순한 11/15 세트를 최종으로 정했다**(4.13). 합쳐도 오르지 않으므로
  둘은 같은 정보를 다르게 담은 것이다.
- **최종 test(방문 10%, 끝까지 보지 않은 데이터)에서 17.0%다**(4.10).
  검증값 16.1%보다 0.9%p 높으므로 세트를 고르는 동안 검증값에 과적합되지 않았다.
  같은 test에서 방어 없는 쪽은 90.6%다. **방어가 90.6% → 17.0%로 막았고, 남은 것은 방어 없을 때의 19%다.**
- **split에서는** 수집 환경 차이가 보이지 않는다. 피처 하나로 낸 AUC는 최대 0.555다.
  split은 pkl 데이터처럼 앞 몇 셀을 잘라낼 필요가 없다.
  **join은 다르다** — `dir_008` 하나로 mon/unmon이 AUC 0.9940으로 갈린다. pkl과 같은 수집 차이가
  그대로 있다(4.14). 방어 없음 비교에 쓰는 join 쪽은 앞 14셀을 버려야 한다.
- **open-world 본 실험**(4.12): 같은 데이터에서 방어만 끄면 binary ROC-AUC가 0.9798 → 0.8203,
  FPR≤1%에서 TPR이 64.7% → 32.0%, 사이트까지 맞히는 TPR_site는 62.6% → 3.6%다.
  **방어는 탐지를 2배, 식별을 17배 깎는다.**
  (join 쪽은 앞 14셀을 버린 값이다. 버리지 않으면 `dir_008` 하나로 mon/unmon이 AUC 0.9940으로
  갈려 "방어 없음"이 부풀려진다 — 다른 팀 확인 요청으로 찾아 고쳤다. 4.14)

## 1. 데이터

| | mon | unmon |
|---|---|---|
| 원본 zip | `mon.zip` (사이트 0–94 × 방문 0–199) | `unmon.zip` (0–18999) |
| 방문 수 | 19,000 | 19,000 |
| 파일 이름 | `{사이트}-{방문}_split_{0-4}.cell`, `_join.cell` | `{번호}_split_{k}.cell`, `_join.cell` |
| 빈 split (뺐다) | 7,962 (8.4%) | 9,953 (10.5%) |
| 쓰는 split | 87,038 | 85,047 |

- 한 줄은 `시간\t방향(±1)\t크기(±512)`이고, 크기는 항상 512다. 기존 pkl 규칙(방향 × 512)과 같다.
- split의 시간은 join의 시계를 그대로 가지고 있다. 파일마다 첫 셀이 0이 되도록 맞췄다.
- split 길이는 중앙값 mon 530셀 / unmon 612셀, 약 9초다(95%가 48초 이내).
  빈 split을 뺀 뒤 50셀 미만은 mon 6.6% / unmon 7.3%이고, 10셀 미만은 1.2%다.
  (11/15 정정: 이전에는 "중앙값 약 400셀, 50셀 미만 약 16%"라고 적었다. 약 16%는 이미 제외한 빈 split을
  포함한 수치였다. `logs/sequences_sliver.log`로 다시 셌다.)
- 줄인 zip은 **부분집합**이다. `mon_75` `mon_50` `mon_25`는 사이트를 줄인 것이고
  (`mon_25` = 사이트 0–24 × 방문 200), `unmon_15000` `unmon_10000` `unmon_5000`은 그중 앞 N개다.
  전체 데이터가 RAM에 들어가므로 받지 않고, 필요할 때 이미 뽑은 피처에서 걸러 쓴다
  (4.11이 `label < N`으로 그렇게 했다).

## 3. 분할 규칙 (누수 방지)

- 같은 방문의 split 5개와 join은 `group` 값이 같다. **train/test와 CV fold는 반드시 group 단위로 나눈다.**
  같은 방문의 조각이 양쪽에 들어가면 점수가 부풀려진다.
- 최종 test는 `ld.sliver_is_test(group)`, 방문의 10%다. 사이트마다 18–23개가 들어가고, 정수 해시라 언제 돌려도 같다. 튜닝 중에는 보지 않는다.
- 빠른 비교(`screen_sliver.py`)는 test를 뺀 방문 중 20%를 검증용으로 쓰는 holdout 1번이다.
  기존 피처 375개로 7.58%가 나와 5-fold 값(7.46%)과 맞는다.

## 4. 결과

### 4.1 기준선 (5-fold, 기존 피처 375개)

| | 정확도 |
|---|---|
| A join→join (방어 없음) | 89.3% ± 0.6 |
| B split→split (방어 있음) | 7.5% ± 0.1 |
| C join→split | 1.4% ± 0.1 |

C가 찍는 수준이다. 방어 전 데이터로 학습한 모델은 split에 통하지 않으므로 학습도 split으로 한다.

### 4.2 split에서 쓸모 있는 피처

- 그룹을 섞었을 때 정확도 하락은 `@timing` −5.0%p, `@cumul100` −2.6%p이고, 나머지 그룹은 0에 가깝다.
- **주의**: `logs/feature_importance_sliver.log`의 그룹 개수는 틀렸다. `ex.groups()`의 기본값이
  pkl에서 구한 준상수 24개를 빼는데, 그 목록은 "모든 기록이 같은 핸드셰이크 14셀로 시작한다"는
  pkl의 성질에서 나온 것이고 sliver에는 그 성질이 없다(BWR이 조각마다 시작 지점을 바꾼다).
  train split에서 재면 `dir_001–014`는 mode_frac 0.70–0.76, `bseq_1`은 0.049로 고유값이 3,929개다
  (준상수 기준 0.9998). 올바른 개수는 `@early` 7 / `@bseq` 30 / `@dir` 100 / `@dir50` 50이고
  `@qconst`는 존재하지 않는다. 코드는 `pkl_qconst=False`로 고쳤고 다시 돌리면 로그가 갱신된다.
  위 결론은 바뀌지 않는다 — 영향받는 그룹은 86개로도 0 근처였다.
  `screen_sliver.py`(4.4)는 `@timing` `@cumul100` `@count` `@burst`만 써서 영향이 없다.
- 방어가 없을 때 핵심이던 방향·순서 피처(`@early`, `@bseq`, `@dir`)는 쓸모없다.
  BWR이 셀 묶음을 무작위 경로로 보내서, 한 경로 안의 셀 순서가 사이트와 무관해지기 때문으로 보인다.

### 4.3 새 시간 피처 (`features_time.py`, 124개)

| 그룹 | 개수 | 내용 |
|---|---|---|
| `tcum` | 38 | 고정 시각(0.25–60초)까지 받은/보낸 셀 수 |
| `tbin` | 40 | 처음 10초를 0.5초 칸으로 나눈 칸별 수신/송신 셀 수 |
| `tnorm` | 20 | 기록 길이를 20등분한 시각까지 받은 셀 비율 (시간 축 CUMUL). **11/15부터 40등분 수신·송신 80개**(5.1) |
| `gap` | 26 | 셀 사이 빈 시간: 임계값별 개수, 가장 긴 10개, 0.2초 넘는 빈 시간이 처음 10번 시작한 시각 |

### 4.4 피처 세트 비교 (holdout, RF 200, 95-class)

| 세트 | 개수 | 정확도 |
|---|---|---|
| 기존 전체 | 375 | 7.6% |
| `@timing` | 18 | 10.4% |
| `@timing @cumul100` | 118 | 7.9% |
| 새 시간 피처만 | 124 | 14.6% |
| **`@timing` + 새 시간** | **142** | **15.5%** |
| `@timing @cumul100` + 새 시간 | 242 | 14.3% |
| `@timing @cumul100 @count @burst` + 새 시간 | 257 | 14.6% |
| 전체 | 499 | 13.8% |
| `@timing` + `tcum` | 56 | 11.3% |
| `@timing` + `tbin` | 58 | 11.9% |
| `@timing` + `tnorm` | 38 | 14.0% |
| `@timing` + `gap` | 44 | 12.5% |

- **피처를 줄일수록 좋아진다.** 쓸모없는 피처가 많으면 RF가 분기마다 무작위로 고르는 후보에 좋은 피처가 덜 들어간다.
- `@cumul100`은 5-fold에서 그룹을 섞었을 때는 중요하게 나왔지만, 넣으면 오히려 떨어진다. 피처 100개가 시간 피처를 묻어 버리는 것으로 보인다.
- 새 시간 피처 중 `tnorm`이 피처 20개로 +3.6%p를 올려 효과가 가장 크다. 기록 길이와 무관한 "로딩 곡선 모양"에 정보가 남아 있다.
- 피처 500개 전체 기준 중요도 상위: `iat_max`, `gap_top_01–10`, `iat_zero_frac`, `duration`.
- 여기 값은 holdout 1번이라 세트 사이 0.5%p 안쪽 차이는 믿을 수 없다. 4.6에서 5-fold로 다시 쟀다.

### 4.5 open-world 수집 환경 차이 확인 (split만, mon vs unmon 이진)

| 세트 | AUC |
|---|---|
| 전체 (499) | 0.805 |
| `@timing` + 새 시간 (142) | 0.816 |

- 피처 하나로 낸 AUC는 최대 0.555(`tnorm_in_*`)다. 한두 피처로 mon/unmon이 갈리는 수집 차이 신호가 없다.
  **단 이것은 split 한정이다.** 같은 확인을 join에서 하면 `dir_008` 하나로 AUC 0.9940이 나온다(4.14).
  BWR이 셀을 경로 5개로 흩어서 split에서는 그 고정 구간이 사라지는 것이고, join에는 그대로 남아 있다.
  pkl 데이터에서는 앞 14셀만으로 AUC 1.0이 나왔다.
- 이진 분류에 쓰인 상위 피처는 `tcum_in_1.5–3`(처음 1.5–3초에 받은 셀 수)과 `gap_at_02–04`다.

### 4.6 세트 확정 (group 5-fold, 시드 3개, `logs/verify_sliver_sets.log`)

holdout 1번으로 고른 세트가 정말 1등인지 확인한다. fold는 `GroupKFold(5)`로 고정하고 RF 시드만 0·1·2로 바꿨다.
세트를 같은 fold에서 짝지어 비교하므로, 차이가 fold 표준편차와 시드 변동폭을 넘는지로 판단한다.

| 세트 | 개수 | 5-fold 평균 | fold 표준편차 | 시드 변동폭 |
|---|---|---|---|---|
| **`@timing` + 새 시간** | **142** | **15.36%** | 0.16 | 0.06 |
| `@timing` + `@cumul100` 10개 + 새 시간 | 152 | 15.14% | 0.15 | 0.21 |
| 새 시간만 | 124 | 14.67% | 0.21 | 0.09 |
| `@timing @cumul100 @count @burst` + 새 시간 | 257 | 14.29% | 0.11 | 0.11 |
| `@timing` + `tnorm` | 38 | 13.95% | 0.29 | 0.11 |
| `@timing` | 18 | 10.66% | 0.32 | 0.15 |

- 1등과 2등 차이 0.22%p가 fold 표준편차 0.16%p와 시드 변동폭 0.06%p를 넘고, 시드 3개에서 순위가 모두 같다.
  142개가 기준선이다. holdout 값(15.5%)은 0.1%p 가량 후하게 나왔다.
- **`@cumul100`을 왜 빼는지**: 100개를 다 넣으면 −1.07%p지만, 10% 간격으로 10개만 추리면 −0.22%p로 거의 사라진다.
  정보가 없어서 떨어지는 게 아니라 **피처 개수 때문**이다. RF가 분기마다 뽑는 후보에 시간 피처가 덜 들어간다.
  그래도 −0.22%p는 fold 표준편차의 1.5배이므로 빼는 쪽을 쓴다.
  본 프로젝트 4.1에서 상관 높은 상위 20개가 하위 20개에 지는 것과 같은 현상이다.

### 4.7 `@tnorm` 확장 (`features_time2.py`, `logs/verify_sliver_sets2.log`)

4.6에서 `@tnorm`이 피처 20개로 가장 효율이 높았는데, 거기에는 (1) 수신만 있고 송신이 없다
(2) 20등분뿐이다 (3) "시각 → 받은 비율" 방향만 있다는 빈틈이 있었다. 셋을 각각 그룹으로 만들어 따로 쟀다.

| 그룹 | 개수 | 내용 |
|---|---|---|
| `tnout` | 20 | 20등분 시각까지 **보낸** 셀 비율. `tnorm_in`의 송신 짝 |
| `tnqin` | 20 | 수신 셀의 k%가 도착한 시각 / 지속 시간. `tnorm_in`의 역함수 방향 |
| `tnqout` | 20 | 송신 쪽 같은 것 |
| `tnfine` | 40 | 수신 비율을 2.5% 간격으로. 20등분이 거친지 보기 위한 것 |

| 세트 | 개수 | 5-fold 평균 | fold 표준편차 | 시드 변동폭 |
|---|---|---|---|---|
| 142개 + 새 100개 전부 | 242 | 16.02% | 0.22 | 0.11 |
| **142개 + `tnout` `tnqin` `tnqout`** | **202** | **15.98%** | 0.20 | 0.01 |
| 142개 + `tnout` `tnqin` | 182 | 15.83% | 0.13 | 0.03 |
| 142개 + `tnout` | 162 | 15.77% | 0.21 | 0.11 |
| 142개 + `tnqout` | 162 | 15.73% | 0.25 | 0.10 |
| 142개, `tnorm_in` 20개 → `tnfine` 40개 | 162 | 15.67% | 0.16 | 0.15 |
| 기준선 (4.6 재확인) | 142 | 15.36% | 0.16 | 0.06 |
| 142개 + `tnqin` | 162 | 15.36% | 0.26 | — |

- **최종 세트는 202개, 15.98%다.** 기준선보다 +0.62%p로 변동폭의 4배가 넘고 시드 3개에서 순위가 같다.
  242개가 0.04%p 높지만 fold 표준편차 0.20%p의 1/5이라 차이로 보지 않고, 피처가 적은 202개를 쓴다
  (`tnfine`은 `tnorm_in`과 정보가 겹친다).
- 가장 크게 올린 것은 `tnout`(+0.41%p)이다. **수신만 보고 송신을 안 본 게 실제 손실이었다.**
- `tnfine`(+0.31%p) < `tnout`(+0.41%p). 20등분을 40등분으로 쪼개는 것보다 송신 방향을 넣는 쪽이 낫다.
  부족한 것은 시간 해상도가 아니라 방향이었다.
- `tnqout`은 **42.7%가 `-1`인데도 +0.37%p 올랐다.** split의 42.7%에 송신 셀이 아예 없기 때문인데,
  BWR이 셀 묶음을 경로 5개에 뿌리면서 수신만 담긴 조각이 생긴다. "이 조각에 송신이 없다"는 사실 자체가
  사이트를 가르는 정보다. 빈 값을 0으로 메웠으면 이 신호가 사라졌을 것이므로 `-1` 센티넬을 쓴다.
- `tnqin`은 혼자서는 +0.00%p다. `tnorm_in`의 역함수라 정보가 겹친다. 빼도 되지만 `tnqout`과 짝을 맞춰 둔다.
- 아직 안 쟀다: `tnout` + `tnqout`만 넣은 182개. `tnqin`이 단독으로 0이므로 이쪽이 더 날씬할 수 있다.

### 4.9 모델 비교 (`models_sliver.py`, `logs/models_sliver.log`)

최종 202개 세트와 같은 group 5-fold를 고정하고 모델만 바꿨다(수업 slide 16). 시드 0.
트리가 아닌 모델은 fold의 train으로만 `StandardScaler`를 맞췄다.

| 모델 | 정확도 | fold 표준편차 |
|---|---|---|
| **RF (200)** | **15.99%** | 0.30 |
| ET (200) | 14.58% | 0.13 |
| LR | 9.70% | 0.25 |
| DT | 7.51% | 0.10 |
| k-NN (5) | 6.64% | 0.10 |
| GaussianNB | 4.25% | 0.12 |

- **RF가 1등이다. 모델 쪽에는 지렛대가 없다.** 2등 ET와 1.41%p 차이로 fold 표준편차(0.13–0.30)의
  5배가 넘는다. 나머지는 6%p 이상 떨어진다.
- **ET가 RF보다 낮은 것이 이 데이터의 성격을 말해 준다.** ET는 분기 임계값을 무작위로 뽑는데,
  여기서는 임계값 자체가 정보다(`gap_at_*`는 "0.2초 넘는 빈 시간이 처음 생긴 시각"이다).
  좋은 피처가 소수뿐이어서 피처를 줄일수록 좋아졌던 4.4·4.6과 같은 방향이다.
- SVC는 뺐다. 커널 SVM은 행 수에 제곱으로 들어 78,331행 × 95클래스는 끝나지 않는다.
- ET 600그루는 `OSError: WinError 1450`(시스템 리소스 부족)으로 터졌다. 원인을 재 보니 **메모리다.**

  | | 나무당 노드 | `tree_.value` | 200그루 | 600그루 |
  |---|---|---|---|---|
  | RF | 59,828 | 45.5MB | 9.1GB | 27.3GB |
  | ET | 103,878 | 78.9MB | 15.8GB | 47.4GB |

  sklearn 트리는 노드마다 클래스별 확률을 float64로 들고 있어 `노드 수 × 95 × 8바이트`가 든다.
  클래스가 95개라 이게 지배적이다. 이 머신은 32GB여서 **ET 600그루(47.4GB)는 애초에 불가능하다.**
  `n_jobs`를 줄여도 안 된다 — 동시에 *만드는* 수만 줄고 완성된 600그루는 전부 메모리에 남는다.
  줄이려면 `min_samples_leaf`나 `max_depth`로 나무를 작게 만들어야 한다.
- **ET 나무가 RF보다 1.7배 크다(103,878 대 59,828 노드).** 무작위 임계값이 그만큼 비효율적으로
  데이터를 가른다는 뜻이고, 위의 "임계값 자체가 정보다"의 직접 증거다.
- RF 200그루도 9.1GB를 쓴다. 다른 프로그램이 메모리를 잡고 있으면 경계에서 페이징이 시작된다.
  `verify_sliver_sets3.py`가 6–15배 느려진 것(같은 fit이 시드 0에서 846초, 시드 1에서 5,383초)이
  그 경우로 보인다. 하드웨어 결함이 아니라 95개 클래스 × 깊은 나무의 예측 가능한 결과다.

**팀원에게 넘기는 것** — 여기서 확인하지 못했고, 하이퍼파라미터는 전처리 담당 범위를 넘는다.

- `mlp`(256, early stopping): 1단계에서 돌지 않았다. RF를 넘을 가능성은 낮지만 비어 있다.
- 모델 비교 시드 1·2: RF-ET 차이가 변동폭의 5배라 결론은 바뀌지 않지만, 표에 넣을 값은 시드 1개다.
- `et600`을 포함한 나무 수 효과: **`n_jobs`를 줄이는 것으로는 안 된다**(위 표). 32GB에서 돌리려면
  `min_samples_leaf`를 2 이상 주거나 `max_depth`를 걸어 나무를 작게 만들어야 한다.
  ET가 RF보다 1.41%p 낮아서 나무를 3배 늘려도 뒤집힐 폭은 아니다.
- RF 하이퍼파라미터(`n_estimators`, `max_features`, `min_samples_leaf`): 4.4·4.6에서 피처가
  적을수록 좋았으므로 `max_features`를 키우는 쪽이 유망하다. 피처 개수 문제가 분기 후보 추출에서
  오는 것이라면 거기서 더 나올 수 있다. `min_samples_leaf`는 정확도와 별개로 **메모리를 줄여서**
  나무 수를 늘릴 여지를 만든다(위 표).
- `verify_sliver_sets3.py`의 시드 2: 206개(`@count` 추가)와 182개(`tnqin` 제외)가 시드 2개에서
  기준선과 0.04%p 안이라 **202개를 유지**했다. 시드 3개째는 리소스 문제로 끊었다.

### 4.10 최종 test (`final_test_sliver.py`, `logs/final_test_sliver.log`)

`ld.sliver_is_test(group)`로 뗀 방문 10%다. 4.6–4.9는 모두 그 10%를 뺀 train 안에서만 돌렸으므로,
세트·모델을 고르는 동안 한 번도 보지 않았다. **보고서에 쓸 숫자는 이것이다.** RF(200), 시드 0·1·2.
스크립트가 train과 test에 같은 방문이 걸치지 않는지 assert로 확인한다(겹치는 방문 0개).

최종 세트(11/15 정의, 4.13)로 다시 낸 값이다. `code/final_test_sliver.py v2`, `logs/final_test_sliver_v2.log`.

| | 피처 | test 정확도 | 시드 변동폭 |
|---|---|---|---|
| **B split→split (방어 있음)** | 202 | **17.01%** | 0.38 |
| A join→join (세트 고정) | 202 | 76.75% | 0.63 |
| A join→join (각자 최선) | 559 | **90.58%** | 0.84 |

참고로 11/19 세트(4.7)로 낸 값은 B 16.51% / A 76.32% / A 전체 90.42%였다
(`logs/final_test_sliver.log`, 인자 없이 실행). **두 세트의 test 차이 0.5%p를 "11/15가 더 좋다"의
근거로 쓰면 안 된다** — test 8,707행에서 정확도 17%의 표준오차가 약 0.4%p이고 group 상관까지 있어
실제로는 더 크다. 4.13의 5-fold 짝지은 비교(표준오차 0.0012)가 훨씬 정밀하고 그쪽은 무승부다.
open-world(4.12)에서도 두 세트 차이가 0.0015로 사라진다.

- **5-fold 검증값 16.08%(4.13) → test 17.01%.** test가 0.93%p 높다. 즉 세트를 고르는 동안 검증값에
  **과적합되지 않았다.** 과적합이었다면 test가 낮게 나와야 한다. 찍기 대비 16.2배다.
- **A를 두 번 잰 이유.** 202개는 split용으로 고른 시간 피처 위주여서 join의 핵심인 방향·순서
  피처(`@early` `@bseq` `@dir`)가 빠져 있다. 세트를 고정하면 **방어 자체의 효과**(76.3% → 16.5%)가
  보이고, 양쪽이 각자 최선을 쓰면 **실제 격차**(90.6% → 17.0%)가 보인다. 보고서에 쓸 것은 후자다.
  A 전체 피처 90.6%는 4.1의 5-fold 값 89.3%(기존 375개)와 맞는다.
- 길이별로도 4.8의 U자가 그대로 재현된다(25–50셀 24.9%, 200–400셀 12.7%, 1600+ 23.1%,
  10셀 미만 1.8%). 검증에서 본 모양이 test에서 무너지지 않았다.
- A의 train은 17,100행, B는 78,331행이다(방문마다 join 1개 대 split 4.6개). A가 적은 데이터로
  90%를 내는 것이니, 격차는 데이터 양 때문이 아니라 방어 때문이다.

### 4.12 open-world 본 실험 (`openworld_sliver.py`, `logs/openworld_sliver.log`)

과제 18쪽 지표를 본 프로젝트와 **같은 정의로** 낸다. 지표 함수(`scores` `at` `report`)를
`openworld.py`에서 그대로 가져와 쓰므로 두 결과를 나란히 놓을 수 있다.
mon = positive(95개 사이트), unmon = negative. 세트 202개, 최종 test, RF.

- `binary` mon(1) vs unmon(0). 점수 = mon일 확률
- `multi` 96클래스(사이트 0–94 + unmon −1). 점수 = 사이트 95개 중 최고 확률.
  `TPR_site`는 사이트까지 맞혀야 정답으로 센다
- 임계값은 `t=0.5`와, unmon 점수 분위수로 잡은 `FPR≤5%` `FPR≤1%`

**같은 데이터에서 방어만 끈 비교** (split = 방어 있음, join = 방어 없음. 같은 피처·같은 분할)

11/19 세트로 낸 값은 binary 0.8213 / multi 0.7363이었다(`logs/openworld_sliver.log`).
**두 세트 차이가 0.0015로 사실상 없다** — 4.13의 무승부가 open-world 지표에서도 확인된다.

- **방어는 탐지를 2배, 식별을 11–17배 깎는다.** TrafficSliver는 "감시 사이트를 봤다"는 사실보다
  **"어느 사이트인지"를 훨씬 잘 가린다.** closed-world(4.10의 90.6% → 17.0%)와 같은 방향이고,
  open-world 지표로도 같은 결론이 나온다.
- **binary(0.8203)가 multi(0.7365)보다 탐지 지표는 높다.** 95개 사이트로 확률을 쪼개면 mon 쪽 확률
  질량이 희석되기 때문이다. **그래도 보고서는 multi를 기준으로 쓴다** — 2026-11-26 수업 공지가
  open-world는 binary(mon vs unmon)가 아니라 **다중 클래스(사이트 95개 + unmon 1개)로 하라**고
  했다. binary 설정은 앞 14셀 수집 차이가 사는 자리이고(4.14), 그 차이는 unmon을 줄이는 과정에서
  우연히 생긴 것이라 일반화되지 않는다. split에는 그 차이가 없지만(4.5) 설정은 공지에 맞춘다.
  binary 숫자는 참고로만 남긴다.
- **`t=0.5` 행은 multi에서 의미가 없다.** 96클래스에서는 최고 확률이 0.5를 넘는 일이 거의 없어
  TPR이 0.45%로 나온다. 보고서에는 FPR 기준 행만 쓴다.
- 앞 14셀을 버리기 전 join의 binary ROC-AUC는 0.9977이었다. 본 프로젝트 pkl도 **버리기 전에는
  1.0000**, 버린 뒤 0.9932다(`docs/OPENWORLD.md`, `logs/ow_modes.log`). 두 데이터셋이 같은 성질을
  보이므로, pkl 값도 참고로 쓸 수 있다.
- **mon:unmon이 약 1:1(0.506)이다.** 현실은 감시 대상이 극소수이므로 **precision은 실제보다 높게
  나온다.** ROC-AUC와 FPR 기준 TPR은 비율에 둔감하지만 PR-AUC·precision은 그렇지 않다.
- **split은 앞 셀을 잘라내지 않는다**(4.5에서 수집 차이가 없음을 확인했다). **join은 잘라낸다**(4.14).
  pkl은 양쪽 다 잘라낸다.
- 누수 방지: mon과 unmon은 `group` 번호가 겹치므로 unmon에 `+10^7`을 더해 분리했다. 더하지 않으면
  서로 다른 기록이 같은 방문으로 취급돼 분할이 깨진다. test는 양쪽 모두 같은 해시로 뗐고,
  unmon은 기록마다 다른 사이트이므로 test의 unmon은 학습 때 보지 못한 사이트다(겹치는 방문 0개).
- multi는 클래스가 96개여서 메모리가 크다(4.9). 나무당 노드를 20그루로 재서 예산 8GB 안에서
  나무 수를 정했다 — split은 103그루(200그루면 15GB), join은 나무가 작아 200그루다.
  나무 수가 다르지만 103 → 200에서 정확도 차이는 거의 없다.
